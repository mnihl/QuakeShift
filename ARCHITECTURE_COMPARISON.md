# QuakeShift: architecture choices and alternatives

These recommendations prioritise a two-person prototype, repeatable experiments and resource-aware operation. Kubernetes, GitHub Actions and Grafana also follow the project's stated requirements. This is a decision proposal for review, not a record of implemented or benchmarked capabilities.

Read alongside [the architecture overview](ARCHITECTURE.md) and [the review checklist](CHECKLIST.md).

| Architecture choice | Popular alternatives | Why proposed for QuakeShift | Trade-off / when the alternative is better |
| --- | --- | --- | --- |
| **Separate ingestion, picker and association processes in one repository** | Single-process application; fully independent microservices | Inference can scale or restart without stopping ingestion. One repository keeps development and versioning manageable. | Adds messaging and deployment complexity. A single process is better for the first experimental detection script; independent microservice repositories would be excessive for two people. |
| **RabbitMQ for queued work** | Kafka; Redis Streams; PostgreSQL job queue | The main requirement is distributing jobs to workers, acknowledging completion and retrying failures. RabbitMQ fits that workflow; historical replay comes from the waveform archive. [Queue documentation](https://www.rabbitmq.com/docs/queues) | It is another service to operate. **A PostgreSQL job queue is a reasonable simplification.** Kafka becomes more attractive when retained event streams and many independent consumers are central requirements. [Kafka overview](https://kafka.apache.org/documentation/) |
| **Separate live and background queues, with reserved live capacity** | One FIFO queue; one priority queue | Catch-up processing must not delay new earthquake detections. Separate worker capacity makes that protection explicit. | Reserved resources can sit idle. A single priority queue is simpler, but priority alone cannot interrupt a long background job already running. |
| **PostgreSQL for jobs, policies, picks and events** | SQLite; MongoDB | These records have clear relationships. Transactions let us save results and pending publications together, supporting consistent recovery. [PostgreSQL transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html) | Requires database administration. SQLite is simpler for a single-process prototype; PostgreSQL better matches shared storage accessed by multiple services. [SQLite guidance](https://www.sqlite.org/whentouse.html) |
| **Waveform files in persistent storage; references in messages** | Waveform blobs in PostgreSQL; S3/object storage | Keeps large recordings out of job messages and separates raw data retention from operational database records. Local files suit the initial cluster. | File availability and retention become our responsibility. Object storage is preferable when workers span multiple machines or deployment moves to the cloud. |
| **At-least-once delivery with deduplication** | Attempting end-to-end "exactly once"; accepting message loss | A crashed worker can retry safely using stable job IDs and idempotent writes. This is a practical recovery model across the broker and database. | Duplicate processing can consume extra energy. Stronger guarantees require careful coordination across every storage boundary; a broker feature alone does not eliminate that work. |
| **Pretrained PhaseNet/EQTransformer plus STA/LTA gating** | One model in every mode; training a custom model | Provides concrete processing policies for testing the accuracy-energy trade-off without adding model-training scope. [SeisBench models](https://seisbench.readthedocs.io/en/latest/pages/documentation/models/waveform_models.html) | More preprocessing and validation work. STA/LTA can miss weak events. **The proposed model ordering must be benchmarked:** EQTransformer is not automatically the best-performing choice on the project's data or hardware. |
| **Local Kubernetes** | Docker Compose; managed cloud Kubernetes | The self-redeployment requirement benefits from Kubernetes' deployment API, rolling updates and workload management. [Deployment documentation](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) | Kubernetes adds substantial overhead. Compose would be a simpler starting choice if automated orchestration were not part of the project. Cloud deployment becomes useful when remote access or additional hardware is necessary. |
| **Small carbon/resource controller** | Kubernetes HPA; KEDA; manual configuration | QuakeShift needs decisions about model selection, station coverage and deferred processing, not just replica count. That application policy needs explicit logic. | Custom control logic needs testing. **Use HPA/KEDA for ordinary scaling if useful**, leaving carbon policy to the controller; avoid two controllers changing the same replica setting. [KEDA scaling](https://keda.sh/docs/2.18/concepts/scaling-deployments/) |
| **Prometheus and Grafana** | Elastic stack; Datadog; cloud monitoring | Queue age, resource usage, latency and carbon intensity are numerical time series. Prometheus collects these, while Grafana presents the operational and experiment dashboards. [Prometheus overview](https://prometheus.io/docs/introduction/overview/) | Requires exporters, dashboards and retention configuration. Managed monitoring reduces maintenance; a log-focused stack becomes useful if searching detailed logs dominates troubleshooting. |
| **CodeCarbon with a simulated carbon signal** | External power meter; real grid-intensity API | Enables repeatable experiments where identical workload runs experience the same carbon scenario. CodeCarbon supplies accessible energy estimates. [Methodology](https://docs.codecarbon.io/3.3/explanation/methodology/) | Estimates are not precise container-level measurements. A power meter strengthens whole-system validation; a real carbon feed is appropriate after the control policy works reproducibly. |
| **GitHub Actions, with a local deployment runner** | Jenkins; GitLab CI; Argo CD | Fits the requested GitHub workflow. A self-hosted runner can reach the local cluster and execute deployment checks. [Runner documentation](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners) | The runner needs maintenance and isolation from untrusted jobs. Argo CD becomes attractive for continuous Git-to-cluster reconciliation; it is additional infrastructure for this prototype. |
